# 0025 · 性能修复第一版：大画布渲染与 studiod 空闲开销

状态：已实现（2026-11-02）

日期：2026-11-01

依据 P1 测量报告（仓库外 `F:/workspace/perf-p1/P1-report.md`，脚本可重跑）。

## 背景

P1 只做测量，结论：

- **画布在 300 到 400 个节点之间卡死。** 300 个节点时平移和拖动都还流畅（103 / 136 FPS）；400、500、1000 个节点各测 5 次，全部卡死，浏览器连基本查询都不响应。500 个节点打开后的前 10 秒里，主线程几乎一直满载：react-markdown 占 45%（`CanvasView.tsx:996`），其余是 React 根节点更新和 React Flow 的尺寸回调。后端不是瓶颈：1000 个节点时 `canvas.get` 只要 18 ms。
- **studiod 空闲时也在消耗 CPU。** 不做任何操作、打开 3 个项目时，每分钟耗 2.9 秒 CPU，约占一个核的 5%。来源是三个每 100 ms 一次的轮询：`gateway.ts:626` 的 flushEvents（每次都重建收件箱和执行槽视图）、`script-batches.ts:350`（每个项目一个 pump）、`generation/src/service.ts:129`。
- **分镜表改一格，会发出约 110 KB 的 `slot.revised`。** 原因是事件里带了整份文档。延迟目前还能接受，这一项留到后续 RFC，因为要改协议。

## 目标与验收指标

用 P1 的测试数据（文本和图片各占一半，文本约 280 字）、P1 的脚本，在本机（20 线程、16 GB）上用普通终端测量：

| 指标 | 现在 | 目标 |
|---|---|---|
| 1000 个节点：打开到可交互 | 卡死 | ≤ 3 s |
| 1000 个节点：平移 / 拖动帧率（requestAnimationFrame 中位数） | 卡死 | ≥ 50 FPS |
| 1000 个节点：打开 5 秒后，10 秒内没有任何操作 | 主线程满载 | 没有超过 50 ms 的长任务，主线程 CPU < 10% |
| 300 个节点：平移 / 拖动 | 103 / 136 FPS | 不低于现在 |
| 空闲 studiod，打开 3 个项目，60 秒 | 2.9 s CPU | ≤ 0.5 s CPU |

功能和交互保持不变：Markdown 显示、双击编辑、选中、多选拖动、画框、连线、节点工具栏、整理画布都要照常工作。现有的 e2e 不改断言、全部通过。

## 不做

- 分镜表事件只携带改动的行（要改协议，留给后续 RFC）。
- 分镜编辑器内部的优化。
- 测试本身的超时和并行度（已经单独处理过：e2e 现在 4 个 worker）。

## 决定

### 1. 画布渲染（`packages/canvas/ui`）

按顺序做，每做完一步就用 P1 脚本复测一次，指标达到就停下：

1. **先找到持续重渲染的原因。** 现在画布没有任何操作时主线程也一直在忙，很可能是 React Flow 测量节点尺寸 → 写回 state → 又触发全部节点重渲染，形成回环。先用 trace 确认，再从根上断开，不要靠防抖掩盖。
2. **节点只在自己的数据变化时重渲染。**
   - `toFlowNode` 对未变化的节点复用上一次的对象（按 NodeView 引用、布局、选中状态、装饰比较）。
   - 节点组件用 `memo` 包起来。
   - 节点通过 context 读取的东西，拆成稳定的 actions 和会变的状态，避免任何一处变化都让全部节点重渲染。
   - 拖动时只替换被拖动的那些节点对象。
   - 连线只在节点的输入关系或选中状态变化时重算。
3. **Markdown 按正文缓存。** 同一段正文只解析一次。缓存可以按正文做 memo，也可以用一个容量有限的 LRU。正文不变时，重渲染不能再次解析 Markdown。
4. **缩小时降级显示。** 缩放低于某个阈值（实现时测量后确定，大约 0.4）时，文本节点只显示截断后的纯文本，不渲染 Markdown；放大后恢复。这一步不能让节点尺寸发生变化。
5. **只渲染视口内的节点**，即 React Flow 的 `onlyRenderVisibleElements`。前四步做完仍达不到指标时才启用。启用前要验证画框、连线、小地图和「整理画布」都正常。

### 2. studiod 空闲循环（`services/studiod`）

维护者 2026-11-01 确认：一起做，用保守的改法，不改成写入处逐一通知（漏一处界面就不刷新）。

- **flushEvents 保留定时器，先做便宜检查。** 每次 tick 先比较一个很便宜的变化信号（例如各已打开项目的事件 seq、全局库的变化、执行槽队列的版本、SQLite `PRAGMA data_version`），全部没变就直接返回，不重建收件箱、执行槽视图和工作卡片；有变化时行为和现在完全一样。信号必须覆盖现在所有会让输出变化的来源，包括连接与订阅的增减、槽位排队；拿不准的来源宁可当作有变化。
- **script batch 的 pump 按需运行。** 没有活动批次（pending_approval / running / paused）时停止定时器；批次发起、批准、拒绝、取消、恢复、生成任务状态变化和启动恢复时唤醒。审批过期仍要按时发生：有 pending_approval 批次时按最近的过期时间安排唤醒。
- **生成服务不动。** 它已按到期时间调度，空闲时每秒只醒一次。
- 行为不变：事件顺序、按 seq 去重、过期、重启后的恢复都和现在一样。现有测试全部通过；补测试验证空闲时 tick 不做重建、没有活动批次时 pump 不再安排定时器、有变化时照常推送。

## 实施拆分

两个 worker 并行。目录不重叠，都不改协议：

- **C1 画布**：`packages/canvas/ui`；如果确实需要，也可以改 `apps/web/src/client` 的 store。
- **C2 studiod 空闲**：`services/studiod`（`packages/generation` 只在确有必要时改）。

两个 worker 都把 P1 的测量脚本复制到自己 worktree 的 `artifacts/perf/` 下，报告里写清改动前后的数字。最终数字由协调者在空闲的机器上用普通终端复测。合并前按惯例跑 code-review medium，再跑 check、build 和两轮完整 e2e。

## 实现时的补充（C2）

- gateway 保留 100 ms 轮询；用各数据库的 `total_changes()` 和 `data_version` 同时覆盖本连接与外部连接写入，并检查连接/订阅版本、项目实例集合、跨日和工作卡片活动节流的到期时间。完整 flush 成功后才提交其执行前的版本快照，任一部分失败则保留待重试状态。跨日判断和工作卡片活动节流均使用 WorkService 同一个注入时钟。
- 第四轮复审恢复整个 flush 的单一异常隔离与全局退避，移除按阶段、项目及连接的失败映射和每连接收件箱/槽位快照，复用原收件箱汇总逻辑。重试期限使用单调时钟 `performance.now()`，间隔从 100 ms 倍增至 1 秒，完整成功后重置；退避期间的 RPC 只记录待执行的强制 flush，到期后补做，不按 RPC 频率重试。失败时保留原工作卡片活动期限，错误键仅保留最后一个；错误键转换和日志异常均被隔离，不能逸出定时器或 RPC 完成回调。
- 已知限制：持续失败的项目或连接会暂停所有项目和连接的推送，直到故障恢复；main 上同类故障会导致 studiod 崩溃。按项目隔离留待后续工作，本 RFC 不实现。
- script batch 仅在有 pending_approval / running 批次时安排下一次 pump；这些批次仍按 100 ms 保守轮询生成任务、媒体任务与脚本变更，审批临近过期时取更早的期限。paused 没有定时过期或自动恢复，等待显式 resume 唤醒；批准、拒绝、取消、恢复和启动恢复均重新安排调度，R3 的条件写入不变。
- pump 返回是否仍需轮询及最近审批期限，正常完成后不再扫描一次状态；异步等待期间的操作使快照失效时才重新读取，并保留立即唤醒请求。pump 或调度查询出错均记录错误；若等待期间收到立即唤醒请求，安排 0 ms 重试并消费该标志，否则安排 100 ms 重试。
- 便宜检查仍需读取已打开项目；其删除恢复记录也按全局库变化信号缓存，避免每次检查重复解码。gateway 和删除恢复共用 studiod 内的版本探针，每个连接复用语句；事务中不返回可缓存令牌，回滚不会留下未提交的删除状态；生成服务不改。
