# 0023 · 脚本节点（第四期 b）：分镜表、资产、首尾帧与批量生成

状态：已实现（2026-11-01）

日期：2026-11-01

设计参考图在仓库外的 `F:/workspace/设计参考图/`：`脚本组件入口参考.png`（连线与生成入口）、`脚本组件示例1.png`（细化编辑分镜表）、`脚本复杂功能参考.png`（资产与合成提示词）。接续 [0021](0021-node-components.md)。

## 背景

现在写分镜只能让 Agent 在画布上建一批文本节点，类别标「分镜」「镜头」（0016）。问题：

- 镜头是散的文本，没有结构：时长、景别、人物、台词混在一段话里，没法排序、批量改、按列看。
- 人物、场景、道具的设定和镜头之间没有关系；同一个角色在十个镜头里各写一遍描述，改一次要改十处，生成结果也不一致。
- 从镜头到生图、生视频要手动复制提示词、手动连参考图。
- 每个镜头各自生成视频，相邻镜头的画面接不上：连续动作在镜头切换处跳变，人物位置、光线突然改变。

0016 当时把「镜头节点」推迟到单独设计，roadmap 里也一直挂着「Shot nodes for storyboards」。本文用**一个脚本节点装一整张分镜表**来做，取代「一个节点 = 一个镜头」的方案（维护者 2026-11-01 确认）。

## 目标

1. 新节点类型 `script`：画布上是一张卡片（剧本标题、镜头数、总时长、前几行预览），展开后是可编辑的分镜表。
2. **剧本拆解和提示词都由 Agent 会话生成**（维护者确认：不新增文本生成服务商，也不用本地模板，因为创作内容无法枚举）。组件负责把剧本、连线的参考和要求交给会话，Agent 通过正式接口写回分镜表。
3. 人物、场景、道具作为**资产**登记在脚本里，镜头引用资产而不是复制描述；资产可以挂一张画布上的图片作为参考图。
4. **首尾帧策略**：每个镜头有首帧、可选的尾帧；相邻的连续镜头共用衔接处的画面，视频用首帧（或首尾帧）生成，镜头切换不跳变。
5. 支持按分镜**批量生成**帧图和视频。用户发起时先确认；Agent 也可以发起，但必须经用户审批后才执行。审批由 gateway 强制，不靠提示词约束。
6. 没有配置生成服务时，建表、编辑、整理照常可用；只有生成帧图和视频调用服务商。

## 不做

- 新的文本生成服务商；本地提示词模板。
- 角色库 / 跨项目资产复用（参考图里的「调取资产」完整页面）：本期资产只属于一个脚本节点（维护者确认，以后再做）。
- 时间线剪辑、按镜头时长自动拼接成片。
- 多人协同的逐格实时合并（见 §3 的冲突粒度）。

## 决定

### 1. 节点与数据

- `CanvasNodeKind` 增加 `script`（`NodeKind` 同步增加；迁移由 `db:generate` 生成）。
- 脚本节点有两个槽位：
  - `main`：分镜文档，新的槽位内容类型 `{ type: 'script', doc: ScriptDoc }`；
  - `prompt`：文本，用来写剧本原文或给 Agent 的要求（参考图「直接在脚本节点输入框内输入剧本内容」）。
- 脚本节点的 `inputs` 可以连文本节点（剧本、设定）和图片节点（参考），和生成节点一样显示为连线。

```ts
ScriptDoc = {
  version: 1,
  rev,                            // 文档级字段（style、sessionId）的修订号
  style?: string,                 // 整体风格，例如「近未来都市软科幻，电影级写实，冷暖对比」
  sessionId?: Id,                 // 负责这个脚本的会话，见 §4
  shots: Shot[],                  // 有序；镜号由顺序得出，不存
  assets: ScriptAsset[],
}
Shot = {
  id, rev,                        // rev：本行修订号，见 §3
  durationSec?: number,           // 0.5–60
  transition: 'cut' | 'continuous', // 与上一镜头的关系：硬切，或画面连续（第一行固定为 cut）
  description: string,            // 画面描述，即首帧画面
  endState?: string,              // 镜头结束时的画面；有它才生成尾帧
  shotSize?: string,              // 景别，自由文本
  camera?: string,                // 运镜
  dialogue?: string,              // 台词 / 旁白
  sound?: string,                 // 音效
  sceneId?: Id, characterIds: Id[], propIds: Id[],
  framePrompt?: string,           // 首帧提示词（Agent 写）
  endFramePrompt?: string,        // 尾帧提示词（有 endState 时）
  videoPrompt?: string,           // 视频提示词：动作、运镜、时长
  promptState?: 'agent' | 'edited' | 'stale',
  color?: 'red' | 'yellow' | 'green' | 'blue' | 'purple', // 行标记
}
ScriptAsset = {
  id, rev,
  kind: 'character' | 'scene' | 'prop',
  name: string,                   // 同一脚本同类内唯一（忽略大小写和首尾空白）；是 Agent 识别资产的依据
  description: string,
  imageNodeId?: Id,               // 画布上的参考图节点
}
```

- 上限：200 个镜头、100 个资产、单格 4000 字；超出返回 `invalid_params`（带原因码）。
- 文本格里可以用 `{{asset:<id>}}` 引用资产，界面显示为名字标签（输入 `@` 唤起，和 0021 的引用标签同一套交互）。资产被删除时标签显示为失效。提示词里引用参考图用 0021 的 `{{ref:<nodeId>}}`，生成时变成「图片 N」。

### 2. 生成结果和镜头的关系

- 节点新增可选字段 `shot: { scriptNodeId, shotId, role: 'first' | 'last' | 'video' } | null`（`NodeMeta`，迁移加列）。分镜表据此在每行显示首帧、尾帧、视频的缩略图和状态，点击定位到画布节点。
- 不把结果节点 ID 存进 `ScriptDoc`：结果节点被删、被复制，都不用回写脚本。同一镜头同一角色有多个节点时，取最新的一个作为当前结果，行内可切换。
- 脚本节点被删除时，结果节点保留，`shot` 引用变成失效；与 0010「删除不级联」一致。

### 3. 编辑接口与冲突

- 新的 `canvas.apply` 操作 `script.patch`：

```ts
{ op: 'script.patch', slotId, ops: ScriptOp[] }   // 一批 1–200 条
ScriptOp =
  | { kind: 'shot.insert', afterShotId: Id | null, shot: ShotInput }      // tempId 可在同批引用
  | { kind: 'shot.update', shotId, rev, fields: Partial<ShotInput> }
  | { kind: 'shot.move', shotId, afterShotId: Id | null }
  | { kind: 'shot.delete', shotId, rev }
  | { kind: 'asset.insert' | 'asset.update' | 'asset.delete', ... }       // 同上，带 rev
  | { kind: 'doc.set', fields: { style?, sessionId? }, rev }               // 文档级 rev
```

- **冲突按行判断**：`update` / `delete` 必须带该行的 `rev`，不一致时整批拒绝，返回 `revision_conflict` 和冲突行的当前内容。这样用户改第 3 行、Agent 同时写第 10 行不会互相打断。槽位本身的 `revision` 每批加 1，用于版本历史（0019 版本条照常可用）。
- 另有 `script.replace`（整份替换），必须带槽位 `expectedRevision`；Agent 第一次拆解或重新拆解时用。
- **提示词过期**由服务端判断：镜头的描述、尾帧、景别、运镜、人物 / 场景 / 道具、转场改变，或它引用的资产改变时，已有提示词的行 `promptState` 变为 `stale`；用户手改提示词的行变为 `edited`，Agent 重写时默认跳过（用户可要求覆盖）。
- 用户的 `script.patch` 是一个撤销步骤；Agent 的不记撤销（与 `canvas.apply` 一致）。
- 事件沿用 `slot.revised`，payload 带完整 `ScriptDoc`（200 行上限内可以接受；大表的增量事件以后再说）。
- `canvas.get` 返回完整文档；Agent 用同一套 `canvas_apply` 工具写。

### 4. 交给 Agent：负责会话

**推荐做法**：每个脚本节点绑定一个**负责会话**（`ScriptDoc.sessionId`）。

- 第一次点「拆解」时让用户选：当前打开的会话（默认）、工作区里的其他会话，或新建会话（选 Agent 类型）。选定后写入 `sessionId`。
- 之后的「拆解」「生成提示词」「修改镜头」都直接发给这个会话，不再询问；分镜表顶部显示「由 会话名 负责 · 更换」。会话归档或删除后，下次操作重新询问。
- 理由：同一个 Agent 记得这份剧本的来龙去脉和之前的决定（人物设定、风格取舍），提示词和镜头前后一致；每次弹窗选择容易发到不同会话，上下文分散。固定发给工作区主会话也不合适：主会话常常在做别的事，而且脚本节点属于项目，不一定在某个工作区里。

发送方式：

- 发送一条**用户可见**的普通消息（`session.sendMessage`），文本是固定的任务说明加用户在输入面板里写的要求，refs 是脚本节点和它连着的输入节点。消息出现在会话记录里，权限、审批、额度照常。
- 任务说明有三种：**拆解**（写镜头、资产、转场和 `endState`）、**生成提示词**（为选中或全部镜头写 `framePrompt` / `endFramePrompt` / `videoPrompt`，引用资产参考图，跳过 `edited` 的行）、**按要求修改**（用户在输入面板里写的任意要求）。说明文本放在 workbench 的 Agent 提示文本里（Agent-facing，可以是中文），界面只放按钮文案。
- Agent 工作时，脚本节点上显示「拆解中 / 写提示词中 · 会话名」，点击跳到会话；依据是这条消息所在回合的状态，不新增事件。
- 各 Agent 的 `prompt.ts` 增加 `ScriptDoc` 写法说明：字段、上限、按行 `rev`、资产按名字去重、`{{asset:id}}` 与 `{{ref:id}}`、首尾帧的写法（首帧写静态画面，尾帧写镜头结束时的画面，视频提示词写动作和运镜），以及「批量生成要用 `script.batch.start`，会等用户审批」。

### 5. 首尾帧策略

镜头切换「怪」的原因是每个视频只从自己的提示词出发，相邻镜头的衔接处没有共同的画面。做法：

- **每个镜头有首帧**（`role: 'first'` 的图片节点）；有 `endState` 的镜头还有**尾帧**（`role: 'last'`）。视频以首帧（和尾帧）作为输入生成：有尾帧时用「首尾帧」模式，否则用「首帧」模式。
**默认流程分两步**（维护者 2026-11-01 选定）：

1. **先批量生成镜头图（首帧）**：每个镜头都生成首帧，包括连续镜头。用户在分镜表里逐行检查、重生成或手动替换不满意的镜头图，这一步便宜，也是参考图所说「检查后再批量」的位置。
2. **再批量生成视频**：所有镜头并行，各自以自己的首帧（和尾帧）为输入。

衔接靠**生成首帧时的约束**，而不是等上一镜视频：

- **硬切（`cut`）**：首帧的输入为该镜头引用资产的参考图。
- **连续（`continuous`）**：首帧的输入额外带上上一镜头的尾帧（没有尾帧时带上一镜头的首帧），提示词写成「接上一镜结束时的画面」，让人物位置、光线、场景延续。
- **尾帧**生成时，输入除了资产参考图，还带本镜头的首帧，保证同一镜头内人物、光线一致；连续镜头的上一镜尾帧和下一镜首帧应当是同一个画面，Agent 写提示词时据此对齐。
- **实际末帧**作为可选的严格模式保留：批量生成视频时可以对选中的连续镜头改用「上一镜视频生成完 → 用 0021 的 `video.frame` 抽最后一帧 → 作为本镜首帧」。衔接最准，但这几镜要按顺序生成。默认不开。分镜表用一条竖线把同一条连续链的行连起来。

**机制归产品，提议归 Agent，决定归作者**（维护者 2026-11-05 修订，原文为“取舍归 Agent”）：首帧、尾帧、帧模式、批次执行是产品提供的固定机制；每个镜头是硬切还是连续、要不要写 `endState`、首尾帧提示词怎么写以保证衔接，是 Agent 在拆解和写提示词时给出的提议，并说明理由，由作者决定和修改（写进 `prompt.ts` 的说明）。效果好不好目前没有验证，第二步实现前先用 mock 走通流程；用真实模型做小规模试验需要维护者另行批准（成本规则）。
- **服务商能力**：模型在 `providers.list` 中新增 `frameModes?: ('first' | 'first_last')[]` 声明支持的帧模式（缺省视为都不支持，只能纯提示词生成视频）。`generation.submit` 新增结构化的 `frames: { first: SlotRef, last?: SlotRef }`，由 provider 适配器映射到自己的参数（方舟映射到它的首帧 / 首尾帧模式；mock 两种都声明）。组件不认识任何服务商的参数名，与 0021 的解耦原则一致。所选模型不支持尾帧时，确认框里说明会退回首帧模式；都不支持时退回纯提示词，并提示衔接无法保证。

### 6. 批量生成与审批

两种批量，入口分开：

- **批量生成镜头图**：为选中（没选时为全部）镜头生成首帧和尾帧。连续镜头的首帧依赖上一镜的帧图，所以同一条连续链内按顺序生成，链与链之间并行。
- **批量生成视频**：为选中镜头生成视频，按 §5 使用首尾帧，默认全部并行。缺首帧的镜头在确认框里列出，可以选择先补生成首帧，或跳过。对开启「实际末帧」的连续镜头，按「上一镜视频完成 → 抽末帧 → 下一镜视频」推进。

批量由服务端执行，关掉页面或 studiod 重启都不中断：

```ts
'script.batch.start':   { callers: both, params: { requestId, scriptNodeId, shotIds?, media: 'frames' | 'video',
                          strictShotIds?: Id[], provider?, model? }   // strictShotIds：改用实际末帧的连续镜头, result: BatchView }
'script.batch.get':     { callers: both, params: { batchId, waitMs? }, result: BatchView }
'script.batch.approve': { callers: ui,   params: { requestId, batchId }, result: BatchView }
'script.batch.reject':  { callers: ui,   params: { requestId, batchId }, result: BatchView }
'script.batch.cancel':  { callers: both, params: { requestId, batchId }, result: BatchView }  // Agent 只能取消自己会话发起的
BatchView = { batchId, status: 'pending_approval' | 'running' | 'succeeded' | 'failed' | 'cancelled' | 'rejected' | 'expired',
              origin: 'user' | 'agent', sessionId?, media,
              estimate: { jobs, billedJobs, model, quotaRemaining },
              shots: [{ shotId, steps: [{ role, status, nodeId?, jobId?, mediaTaskId?, error? }] }] }
```

- **用户发起**：界面先弹确认框，写明镜头数、任务数、所用模型、是否计费、预计占用的今日额度，以及提示词为 `stale`、资产缺参考图、模型不支持尾帧的镜头数（参考图「不建议直接批量生图」，这里提醒但不阻止）。用户确认后才调用 `script.batch.start`，批次直接进入 `running`。
- **Agent 发起**：`script.batch.start` 返回 `pending_approval`，不提交任何任务。审批卡片出现在该会话的记录里（新的审批类型 `generation_batch`），同时在脚本节点上提示。卡片内容和用户确认框相同。用户批准后开始执行，拒绝则为 `rejected`；24 小时未处理为 `expired`。Agent 可以用 `script.batch.get` 等待结果，回合结束不影响审批。**这是 gateway 的强制规则**：Agent 调用没有任何参数能跳过审批。批准时如果分镜表在请求之后改过，卡片会标出变化的镜头。
- **执行**：每一步对应一条 `generation.submit`（`requestId` 由批次 ID、镜头 ID、角色派生）或一个本地抽帧任务，所以重试、重启续跑都不会重复提交、重复计费。结果节点放在脚本节点右侧，每个镜头一列（首帧、尾帧、视频），类别「镜头」，标题「镜头 N · 首帧」等，带 `shot` 元数据。
- **额度**：每个任务照常计入每日总量，额度用完时批次暂停在当前步，标明原因。Agent 发起、用户批准的批次**不占 Agent 的每日上限**（维护者确认：用户已逐项看过并批准）；`estimate` 和审批卡片照常显示占用的总量。
- **进度与取消**：分镜表每行显示各步状态；可以取消整个批次。已提交的任务按现有规则取消，取消不等于退款，按 `providerCancelled` 如实显示。
- 批次存在 `space.db` 新表 `script_batches`；事件 `scriptBatch.stateChanged`；快照带未结束的批次。

### 7. 展开后的分镜表（参考图的三步）

顶部三个步骤标签，和参考图一致，但不强制按顺序：

1. **确认镜头**：表格逐格可编辑；行可以新增、删除、拖动排序、标颜色、切换转场；多选后批量设置时长 / 景别 / 场景。每行显示首帧、尾帧、视频缩略图。
2. **准备资产**：按人物、场景、道具分组的卡片。可以改名字和描述，挂参考图：从画布选一个图片节点、上传，或「生成参考图」（新建图片生成节点，提示词由负责会话写，类别为「人物 / 场景 / 道具」，不自动提交）。底部提示还没有参考图的资产数量。
3. **生成提示词**：「为选中 / 全部镜头生成提示词」发给负责会话；每行显示提示词状态（Agent 写的、手改过、已过期），可以直接手改。

画布上：收起时卡片显示标题、镜头数、总时长、前 3 行摘要、资产数，以及 Agent 工作中或批次进行中的状态；展开时在原位放大成全屏编辑层（和 0019 全屏预览同一类外壳），Esc 关闭，表格虚拟滚动。0021 顶部工具条对脚本节点显示：展开、拆解、生成提示词、批量生成镜头图、批量生成视频、下载（导出为 CSV / Markdown，本地完成）。

会话引用与工作审阅使用脚本表格图标；引用预览和审阅前后版本显示脚本标题、镜头数与资产数，计数使用对应文档修订。

## 实现时的补充（S1）

- `slot_revisions.script_doc` 用 JSON 保存完整文档，沿用不可变修订、版本历史和回合快照；`nodes.shot` 用可空 JSON 保存关联，不设外键，删除脚本不清理结果节点的关联。
- 脚本节点默认 480×320，创建时 `main` 包含 `EMPTY_SCRIPT`，`prompt` 即使为空也建立文本修订。镜头和资产由服务端分配带 `shot_` / `sast_` 前缀的标识；结果包含在 `canvas.apply.idMap`，供同批后续操作使用。
- 行冲突沿用 `revision_conflict`，原因码为 `script.revision_conflict`；`params.currentRows` 是 JSON 字符串，解析为 `{ kind: 'shot' | 'asset' | 'doc', id?, current }[]`。CLI 和 MCP 保留原因码与参数，不需要扩展现有错误契约。
- 逐条执行操作并递增所改行的修订，资产改名、描述或参考图会递增引用镜头的修订；移动造成首行转场归一化时，该次操作对移动行只递增一次。资产删除清理结构化引用，保留文本里的失效标签，符合界面显示失效资产的约定。
- 同一条镜头更新同时改来源与提示词时，新的提示词按写入者标为 `agent` / `edited`；仅改来源时变为 `stale`，全部提示词清空时状态清空。普通台词、音效、时长与颜色不参与来源过期判断。
- `script.replace` 省略 `style` / `sessionId` 时保留原值，显式 `null` 才清空，避免重新拆解意外解绑负责会话；替换会递增文档级 `rev`，旧的 `doc.set` 不能跨替换覆盖文档字段。

## 实现时的补充（S2）

- `script_batches` 由 drizzle 生成迁移，保存公开批次状态与内部执行图、原始参数、请求时的行修订、已解析的提交参数。纯规划器不写数据库；执行器按依赖推进，同一连续链顺序执行，独立链可同时提交。
- 批次模型选择与单节点提交一致：显式参数优先，其次脚本节点保存的生成设置，最后采用当前媒体类型的全局默认。视频批次补生成首帧时，首帧另用图片类型的默认模型。
- 生成步骤的请求标识固定为 `batchId:shotId:role`，建节点与抽帧也使用派生标识。提交前先保存输入与目标的具体槽位修订；重启时先重放已提交请求，再检查剩余额度，避免在提交成功但批次尚未保存任务标识的窗口重复计费或错误暂停。抽帧任务若因重启中断，可重用同一本地任务恢复，不重新提交生成。
- 服务端没有用户语言上下文，持久化节点标题采用本文允许的固定中文回退：「镜头 N · 首帧／尾帧／视频」，类别「镜头」。列对应本批选中的镜头，镜号仍采用当前文档中的原始序号；抽帧沿用媒体任务产生的图片节点，补上位置、标题和镜头关联，不另建重复图片。
- `frames` 按显式修订、回合快照、当前修订的优先级固定，记录在生成任务中，并与普通输入一起保留来源；适配器得到独立的结构化 `frames`。mock 与方舟视频模型声明两种帧模式，本地 render 不声明。方舟的结构化帧覆盖 `imageMode`，同时带媒体参考输入会在占用额度前以原因码拒绝。
- mock 图片的 PNG `tEXt` 保存 `Inputs`、`Frames` JSON；mock 视频末尾保存 `VIS_INPUTS:`、`VIS_FRAMES:` JSON 行，供无模型测试检查实际收到的素材路径。画布的 `inputs` 与任务固定的槽位修订仍是正式来源信息。
- Agent 发起时只创建 `generation_batch` 审批记录，绝不提交任务，`auto` 模式也不绕过；只有 UI 的批次批准／拒绝方法能处理此记录，普通 `session.respondApproval` 返回原因码。审批与回合生命周期独立，重启后保留，24 小时后过期；批准时重新规划并返回修订变化的镜头标识。
- 待审批批次的 `get`／`list` 只读计算 `changedShotIds`，对照请求时保存的行修订，包括已删除的镜头；后台调度也发布带当前变化列表的批次事件，不提交生成。批准时忽略已经删除的显式选中镜头，并按当前仍存在的镜头重新规划。
- 经用户批准的任务以用户额度身份提交，计入每日总用量而不计入 Agent 用量；批次按当前媒体的每日总量检查额度，耗尽后暂停，用户恢复时继续未完成的步骤。取消保留生成任务的真实 `providerCancelled`，不把本地停止解释为退款。
- 严格连续模式依赖上一镜视频成功，再调用 `video.frame`，时间设为媒体总时长。媒体服务对总时长（含原有 50 毫秒容差）直接解码末尾片段并保留最后一帧，避免停在最后帧时间戳之后；其他抽帧时间不变。此小范围 `assets` 修改已由协调者确认，另有非整帧边界的末帧回归测试。
