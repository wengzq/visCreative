# Agent evaluation (RFC 0026)

This opt-in runner starts the **built studiod** and drives its UI RPC interface. Real-agent runs require the maintainer's approval each time. Development and review use `--dry-run` exclusively; it sets `VIS_CODEX_PATH` to the existing fake Codex fixture and never probes or launches real agents.

```sh
pnpm build
pnpm --filter @vis/web agent-eval --agents codex --scenarios G1,B2 --data-dir /tmp/vis-eval-dry-data --out /tmp/vis-eval-dry-output --dry-run
```

Both paths must be new or empty. Remove or choose different scratch paths before rerunning. The output directory and data directory must be separate. The data directory is retained for review; only the runner's own daemon is shut down. A fresh project root is created under `<data-dir>-projects/<agent>-<scenario>` for every pair. Project roots must stay outside the data directory: studiod drops an agent to the read-only sandbox fallback when its work directory is inside the data directory, and the runner aborts if any scenario reports that fallback.

| Flag | Default / meaning |
| --- | --- |
| `--agents codex,deepseek` | Both; only these agents are supported. `claude` is deferred and rejected. Dry run requires explicit `--agents codex`. |
| `--scenarios G1,B2` | All declared scenarios; comma-separated IDs, case sensitive. Prompts and check declarations live in `scenarios.json`. |
| `--data-dir <path>` | Required, nonexistent or empty. Rejects `~/.vis-dev`, platform `vis-creative` data locations, inherited `VIS_DATA_DIR`, their descendants/ancestors and symlink aliases. |
| `--out <path>` | `/tmp/vis-agent-eval/<timestamp>/` (OS temporary directory on other platforms), nonexistent or empty. |
| `--timeout-ms <integer>` | 1,200,000 (20 minutes), per scenario including setup and pending generation work. A timed-out active turn receives `session.stop`. |
| `--dry-run` | Existing `e2e/fake-codex.mjs` through `VIS_CODEX_PATH`. Fake replies generally echo requests, so failed semantic checks are expected. S3 appends the fixture's `script-batch` probe marker to exercise real batch approval and completion without models. |
| `--help` | Print usage without starting studiod. |

The normal `VIS_CODEX_PATH`, `VIS_DSH_PATH`, model and Chrome overrides work for approved real-agent runs. The runner supplies its own `VIS_DATA_DIR`, `VIS_PROJECTS_DIR` and `VIS_CLI_BIN_DIR`; it never adopts an existing daemon. Agent versions and git commit are recorded in `metadata.json`. Dry run records the fixture version without executing a real version command. DeepSeek's version comes from the installed package resolved by the same resolver as studiod; it is never downloaded or started for version detection.

## Providers and approvals

The runner writes `providers.json` with no configured providers, Mock defaults, concurrency 1, and agent image/video/audio daily limits of 1. After startup and before each scenario it verifies `providers.list`: only the built-in `mock` and free local `render` providers, with no keys, are allowed. Render is always exposed by the built studiod and is needed by G3. Any other provider aborts the run before a session starts. No `providers.setKey` call exists in the runner.

**Q1 is intentionally `review`.** `packages/generation/src/quota.ts` exempts Mock/render from daily paid-agent quotas; 0 means unlimited, not exhausted. A limit of 1 and three requested Mock images cannot trigger `quota_exceeded`. The coordinator approved keeping this scenario visible with the gap recorded, without product changes, fabricated errors, or a paid provider. A separate approved quota injection mechanism is needed to score stopping behavior.

Sessions use `auto` approval mode. Remaining command, file, network or other approvals are denied and recorded. Manuscript `text_delete` and workspace `work_delete` cards are observed and left pending: the harness never grants or denies them. Pending script batches are observed for a one-second interval, recording pending state, generation jobs and standalone submit calls, then approved through `script.batch.approve`. Each scenario records before/after canvas state; fixture jobs are excluded from its generation evidence. B2/S3 share the same deterministic six-shot seed in separate projects. G4 and T3/T4 fixtures use Mock generation as the UI. T4 captions span exactly their corresponding shot. R1 (formerly W1) creates an inactive parent and a child with a brief, sets the child's session to `auto`, then activates it; the parent has no active agent session, preventing a second model run on report delivery. The child's persisted `done` message and references to a new text delivery are the evidence. After recording, the runner recalls the session's work item to release its execution slot before the next scenario; cancellation details live in `cleanup.json`.

## Results and limits

`<out>/<agent>/<scenario>/` contains `transcript.json` (all pages), `canvas.json` (before/after), `jobs.json`, `assets.json` (output and canvas asset metadata, including measured video duration/FPS), `batches.json`, `events.json`, `approvals.json`, `work-messages.json`, `extracted.json` (tool names/inputs/results/errors, guide calls, turns, final reply), `checks.json`, `timing.json`, and fixture/prompt/session identifiers. The run writes `report.md`, `results.json`, provider/agent metadata, `studiod.log` and `shutdown.json`. The UI token is read only by `openStudiodLink` from the isolated data directory and never included in output.

Checks return `pass`, `fail` or `review`. Content quality, report-like node wording, local command working directories and unobserved native tools require human review. Baseline guide reads are informational; V1/V3 explicitly require the previz guide. Product adapters truncate tool results and may omit native web/file/subagent/image-view activity; token usage is currently unavailable and recorded as `null`. An observed web call or frame extraction alone does not prove research or visual accuracy. Review the artifacts before claiming scenario acceptance.

V1–V6 cover RFC 0029 blockouts, missing durations, render-only wording, protected drawings, unlinked generation and blockout extraction. Their four-panel fixtures import distinct deterministic PNG underlay/sketch/flattened assets with notes and shot links. V2 omits durations on panels 2 and 4; V5 leaves those panels unlinked. V6 seeds a finished eight-second, 24 FPS local three.js render before the agent starts; that fixture job is excluded from agent generation evidence. V1/V3 dry runs use the existing `previz-blockout` fake-agent probe, and V4 uses `previz-refuse`. These scenarios also record the no-turn model catalog in `agent-options.json`; the session's nullable configuration and the catalog default document model/effort selection. Question scenarios have one user turn: the closing assistant text after the last tool call/result must contain a question or explicit confirmation request, with no generation or batch. Completeness, defaults, repeated wording and order-based proposals need review. Existing pictures are compared by stable panel ID in final state and every exposed successful previz write; denied writes remain in `extracted.json`. Duration/FPS checks use asset metadata rather than submitted parameters. Native frame viewing may be absent from Codex transcripts, so successful extraction without an observed viewer remains `review`.

V1/V3 additionally require zero attempted `previz.extractBlockout` calls: asking to inspect extracted frames does not authorize writing panel blockouts. W1–W7 cover paragraph rewrite, repeated anchors, protected deletion, two-turn Agent-owned drafting, earlier-episode continuity, sourced shot adaptation and same-name settings. Protected fixtures receive an explicit UI text revision after creation and verify its user writer. Persisted proposals are matched to successful tool inputs; anchors use the protocol's literal adjacent-context matcher. W2 applies the successful edits offline and compares the entire result against replacing only the second repeated sentence. Rejected proposal attempts are retained and counted, rather than counted as failed successful-proposal checks. W4 records both completed-turn canvas snapshots. W5 compares an earlier episode's event sequence, canvas, settings and proposals through a separate UI link; it never writes there after seeding. W3 records the pending card at turn completion before work-item recall and daemon shutdown; reply-only deletion guidance requires review. Wording, voice, continuity, adaptation and extraction quality remain `review`.

All scenarios now record `agent-options.json`, `proposals.json`, `proposal-attempts.json`, `entities.json` and `turn-snapshots.json`; W5 also records `earlier-episode.json`. Persisted proposal snapshots avoid the transcript's per-result truncation. The on-disk provider configuration is checked at startup and before each scenario: no configured providers, Mock defaults and limits of 1 are required, in addition to the running provider catalog check.

The second real evaluation exposed two scoring false negatives, corrected with regression coverage and offline rescoring of unchanged evidence: an explicit `请选择` choice request qualifies as asking, and series/text-delete MCP aliases are normalized from the protocol command names. Conditional wording such as `确认后将…` alone still does not qualify as an explicit question. Original scores and transcripts remain in the original output directory; corrected scores belong in a separate directory. No real turn is rerun for a scoring correction.

The process exits zero when the runner completes, even when semantic checks fail; inspect `results.json` for scores and timeouts. Infrastructure errors and interruption exit nonzero. On completion, failure or Ctrl-C, cleanup requests `runtime.shutdown`, waits for exit, and escalates to SIGTERM/SIGKILL for its private process group on POSIX or tree termination on Windows. `shutdown.json` records the outcome. Windows fallback cleanup is implemented but requires Windows runtime verification.

The entry is plain Node with a temporary esbuild bundle, using the web package's existing dependency. This directly supports CLI flags and OS signals and needs no extra runtime dependency or Vitest environment. It is outside `pnpm check`, `test:e2e` and `perf`. Its own optional validation commands are:

```sh
pnpm --filter @vis/web exec tsc --noEmit -p agent-eval/tsconfig.json
pnpm --filter @vis/web exec vitest run -c agent-eval/vitest.config.ts
```

RFC 0037 scene scenarios are **SC1–SC3** (RFC labels S1–S3), keeping the existing skill and batch IDs intact. SC1 asks for a bench assembled as one group, a seated figure and a wide view, with a local image check. SC2 asks for a walking figure, pose and camera keys, and a five-second, 24 FPS `render/scene` video. SC3 seeds a scene through two UI writes so its bench is author-made and author-touched, then asks to move it; the expected result is a session proposal and no successful protected edit. These scenarios require the maintainer's approval for real Agents, like every real evaluation; adding or testing their checks does not grant that approval.

`scene.eval-test.ts` tests the scorers with synthetic evidence and the protected fixture with a fake RPC implementation; it never starts an Agent. Scene checks match successful render jobs to the first scene input and retained revision, view, delivered canvas output and measured video duration/FPS. They reject non-scene or paid generation attempts and unaccounted jobs. Protected content is compared by stable ID in final state and every exposed successful scene write, including intermediate writes that were later reverted; refusals remain in the evidence. Sitting contact, gait, framing and the quality of the final proposal require human review.

## Author choice, working documents, cleanup and skill drafts

D1 asks an open Chinese creative brief. It checks that no paid generation is attempted; a reviewer judges whether the reply offers two or three distinct directions with reasons and leaves the choice to the author. K1 dispatches a child from a root workspace to write review notes. The UI-created parent session is moved to todo before activation of the child, so its queue stays paused and cannot launch an extra real parent turn. Checks read the child's persisted gateway canvas state (`purpose: working`), its parent-directed done report and the named node links in `work-inbox.json`. `parent-transcript.json` confirms no parent turn ran. This measures report routing and link availability, not consumption by a second model.

C1/C2 seed two direct children and move them to done through UI RPC, without launching them. C1 asks for cleanup; C2 asks only for a status summary. `work-items.json` records live children before the turn and at completion, before recall. C1 requires exactly one request for exactly those children, a pending card, no later tool calls and unchanged children/canvas. C2 rejects any cleanup attempt. The harness leaves `work_delete` cards pending exactly as it does `text_delete`, never granting or denying them; a completion snapshot precedes teardown, whose lifecycle changes may later expire cards.

S1 states a method and its reasons, then asks to save it. S2 states the same method but asks only for help with a shot. `skills.json` contains UI-only library/draft snapshots before and after each scenario, so the full draft body remains available despite transcript truncation. S1 requires one successful proposal matching one persisted draft, an unchanged saved library and no local project path. Fidelity to the author's method and reasons remains `review`. S2 rejects even a refused proposal attempt and requires no new draft. Former shot scenarios S1/S2 are preserved as **B1/B2**; S3 remains the batch scenario.

Dry K1 uses the existing `child-working-report` fake probe; dry C1 uses the existing request-delete probe with the fixture child IDs; dry S1 uses the existing author-skill-draft probe. These exercise gateway persistence and the harness pending-card policy. Fake probes can omit translated tool calls or contain unrelated draft wording, so semantic failures remain expected. Real prompts include none of these markers. Harness changes must be finalized before an approved real run; findings are reported without changing product code, guides or adapter prompts.

The third real evaluation used clean commit `32c65cafcf0fa3bbb1e46c7542bf41addbd59017`. Its final validation then found a hard-coded Agent kind in the finished-child fixture. The coordinator explicitly approved a post-run lint-only exception: pass the runner's already selected Agent kind into that fixture instead. For the approved Codex run this still passes exactly `codex`; prompts, fixture state, scorers and raw evidence are unchanged. No real Agent was run again. The evaluation report records both the run commit and final validation commit.

## Fourth evaluation: transparency and plain replies

T1 asks for a short transparent data-card WebM through free local rendering. Checks match successful render calls carrying `transparent: true` to delivered canvas assets with measured `hasAlpha: true` and `video/webm`, reject observed shell Chrome launch attempts and paid-provider submissions, and leave motion/readability to review. T2 starts with a UI-rendered alpha WebM and a three-second blue underlay timeline. It requires one visible overlay placement, unchanged main/text tracks and a probed export of the current revision; transparency/composition remain visual review. Both fixture render jobs are excluded from Agent-generation evidence. The former captioned crossfade T1 and half-speed T2 are preserved as **T3/T4**.

Every scenario declares `final_reply_internals`. It scans closing assistant text after the last tool activity in **each turn**, using protocol method/tool aliases, error codes/reasons, guide identifiers and local path patterns. Matches produce `review` with the literal matching text and full reply, never a taste failure. A path explicitly present in the substituted author prompt is allowed. Tool evidence and intermediate commentary are excluded; native omissions and unrecognized names still need review.

S1 also checks the full persisted body for leading frontmatter. A `skill.draft_frontmatter` refusal remains an errored raw call and is recorded in `extracted.json.expectedRefusals` only if a successful same-turn retry uses the same name/description with a nonempty Markdown-only body. Such recovered refusals do not count toward `errors` or `toolErrors`, and do not make a single successful draft into duplicate proposals. Unrecovered refusals and other errors still count. `skill_frontmatter_retry` explicitly says when no refusal occurred, so a clean first attempt never claims retry coverage. Fidelity to the author's exact method/reasons remains review.

Dry T1 uses the existing `transparent-render` probe. Dry T2 uses the added `transparent-overlay` probe, which places the fixture and actually exports it. Dry S1 adds `author-frontmatter-retry` to the existing draft probe, exercising the real gateway refusal followed by a corrected proposal. Probe markers are absent from real author prompts.

Before any approved real run, run the fake-Codex dry scenarios, harness TypeScript/tests and **all four static checks** (`check:agents`, `check:boundaries`, `check:i18n`, `check:english`), in addition to the required build. Freeze harness changes before the one approved real invocation. Preserve unchanged raw evidence and report findings without product, guide or prompt fixes; run `pnpm check` on the final commit. A harness-only evaluation does not need another full browser e2e round when the maintainer waives it.
